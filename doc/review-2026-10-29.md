# imlresi review, 29 Oct 2026

Scope: `trace.py`, `dotresi.py`, packaging, docs and tests at 0.0.46 (commit
054a3a4, plus the uncommitted feed-speed fix, which checks out as
consistent). "Confirmed" means someone reproduced it by running code.

Fixes are tracked in the checklist at the end.

## 1. Correctness bugs

### Critical

- **Loading a real FQResi file throws away DOB** (`dotresi.py:780-788`).
  Real files have both `DBHOB` (all NA) and `DOB` (the value). The loop takes
  the first match, `DBHOB`, sets `DOB = None` and deletes `DBHOB`. Confirmed on
  `2_FWPA_4.8.0.Resi`: raw DOB `[339.5, 287.0]` loads as `[None, None]`.
  Knock-on effects: recomputed corrected traces treat DOB as 0; `to_dotresi`
  and `change_instrument_id` write the file back without DOB; in Delta the
  all-null column gets type `void`, so later merges fail.
- **A Delta merge can overwrite the whole table** (`dotresi.py:1440-1450`).
  Table existence is checked with `Path(table_path).exists()`, which is false
  for a `DeltaTable` (`file:///` URI) and for `abfss://` or `s3://` paths, so
  the code calls `write_deltalake(mode='overwrite')`. Confirmed: a table
  holding a, b, c merged with z ended up holding only z. The Spark path does
  the same thing: when it can't find the table it swallows the error and
  overwrites (`1323-1360`).

### High

- **Both `.Resi` write layouts have the wrong columns** (`DF_COLUMN_TYPES` /
  `LEGACY_DF_COLUMN_TYPES`, `43-129`). Writing 4.8.0 drops `MOEmodel`,
  `CheckStatus`, `AdjustRecord`, `DOB`, `Version`, `EqnType` and
  `RadialMOEMethod`. The 4.2.4 writer adds `CheckStatus`, `AdjustRecord` and
  `EqnType`, which real 4.2.4 files don't have, so the layouts look swapped.
  Without `EqnType` an "Ln" calibration silently becomes "Linear"; without
  `Version` a different standardisation is picked.
- **The file-version check never works on real files.** Both samples store
  `version` as `x86_64-pc-linux-gnu`, so `change_instrument_id` silently
  converts 4.2.4 files to the 4.8.0 layout.
- **`change_instrument_id` leaves the old ID in `ringData`** (confirmed). The
  branch meant for `r.trace` never runs (`1514`).
- **`save_traces_to_dotresi(append=True)` duplicates rows** (confirmed).
  Saving the same trace twice gives 2 rows in `df` but 1 entry in
  `resTraces`, so the file no longer agrees with itself.
- **`Trace.get_bark_thickness()` gets the exit bark wrong** (`trace.py:979`).
  It uses `DOB - UBDIA`, the bark on both sides added together, without
  subtracting the entry bark. `test_trace.py:281` asserts the wrong value.

### Medium

- **Dates and times** (confirmed): the day-first fallback swaps day and month
  on ISO strings; `03/04/2022` is read month-first, contradicting that
  fallback; `save_traces_to_dotresi` uses only `header['date']`, so every
  SampleDate comes out as 00:00:00. The test's mock trace has a `dateTime` key
  that real traces don't have, which hides this.
- **`Trace.__str__` prints the drill data under the feed heading**
  (`trace.py:627`, confirmed).
- **`Trace`, `ResiResult` and `ResultSet` can't be copied or pickled**:
  `__getattr__` raises `RecursionError` (confirmed). That breaks
  multiprocessing and Spark workers.
- **Mistyped `get_` methods don't fail.** `Trace.__getattr__` turns any
  `get_*` call into a getter: `tr.get_feedsped()` returns `None` instead of
  raising `AttributeError` (confirmed).
- **`process_using_resiapi` with a `Path` raises a raw `TypeError`**
  (`PosixPath` isn't JSON-serialisable), not a `ResiAPIError` (confirmed). It
  also sends the full local file path to the server.
- **The Windows classifier is misleading.** Files are opened without an
  encoding, so under cp1252 the `°` and `±` characters get garbled and
  `get_latlon()` returns `(None, None, None)` for every `.pdc` (confirmed by
  simulating a cp1252 locale).
- **Missing or NA values in the recompute functions.** `Standardised = pd.NA`
  raises `TypeError`; a missing `TraceType` raises `AttributeError`; NaN gets
  past `x or default` and turns whole traces into NaN. `to_dotresi` hides these
  failures and leaves `denTraces` out.
- **DuckDB export.** `ResiFile` stores the trace name, not the `.Resi` path. A
  missing RPMCoef is stored as a made-up `-0.8`. The duplicate check ignores
  EqnType and Resource. A failed insert leaves the transaction open (no
  rollback). IDs come from `MAX(id)+1`, which isn't safe with concurrent
  writers.

### Low

- `read_bin` on bad input fails with an `assert` (stripped under `python -O`)
  or a `ZeroDivisionError` when `drill_depth` is 0.
- The default ResiCode differs by code path: `PD500-0000` in one place,
  `PD400-0000` in two others.
- `feed` is `[]` from bin files but `None` from txt1 files.

## 2. Security

The risky inputs are caller arguments and the files the library parses.

- **SQL injection through `table_prefix`** (`914-1005`). Confirmed: one value
  dropped an existing table, because DuckDB runs several statements from one
  string. `from_duckdb` also runs a caller-supplied `sql_query` and builds
  `IN {trace_ids}` from values read back from the database. Validate
  identifiers (`^[A-Za-z_][A-Za-z0-9_]*$`) and use parameters.
- **Delta merge keys go straight into the merge predicate** (`1475`, `1313` on
  Spark). Check them against the DataFrame's columns.
- **Hostile `.Resi` files are parsed with no limits.** `rdata` loads the whole
  file into memory, so a gzip bomb or a huge declared vector length can
  exhaust it, and all of `rdata`'s warnings are suppressed. `rdata` doesn't
  run code, so the risk is denial of service.
- **Paths outside Fabric get rewritten.** `normalize_filepath` turns any
  relative `Files/…` path into `/lakehouse/default/…` and drops the first
  folder of a non-OneLake `abfss://` path. Reading uses it, `to_dotresi`
  doesn't, so the same URI behaves differently for reading and writing.

## 3. Design weaknesses

- **Dependencies.** `duckdb` and `rdata` are imported at module load.
  `deltalake`, `pyarrow`, `pyspark`, `delta-spark` and `matplotlib` are
  imported lazily but never declared, not even as extras. `numpy <2.0` forces
  source builds on Python 3.13. Suggested extras: `[delta]`, `[spark]`,
  `[plot]`, and a `[test]` extra that includes deltalake.
- **Hidden global state.** Importing pyspark anywhere switches the Delta code
  to the Spark path (`1294`). `spark.conf.set(autoMerge…)` is never restored.
- **Errors are swallowed.** 15 `except Exception` blocks in `dotresi.py`, most
  of which pass or downgrade. With the merge-overwrite bug, a swallowed error
  becomes data loss.
- **`ResiResultSet` is a god class** (641-1900): RDS I/O, DuckDB store,
  Delta/Spark export, API ingestion and ID rewriting. The API-response parsing
  is copy-pasted between `load_traces` and `save_traces_to_dotresi`.
- **`Trace.hash()` depends on ujson's output** (md5 of `ujson.dumps`), so a
  ujson upgrade or formatting change silently changes it.
- **Library logging.** `loguru` writes to stderr unless the app disables it,
  and errors are both logged and raised.
- **`assert` is used for input checks** in `read_json` and `read_bin`.
- **`get_latlon` only handles the southern and eastern hemispheres**.
- **`Trace.x` and depth in `save_traces_to_dotresi` assume 10 samples/mm**
  instead of reading the trace's settings.

## 4. Inconsistent documentation

- The README shows only `Trace.read` and `to_json`. The `main()` CLI has no
  `[project.scripts]` entry.
- The `to_deltalake` docstring says it returns a DeltaTable; it returns a
  `DeltaMergeResult`, or `None` for an empty set.
- `format_version` defaults to `4.2.4` in `save_traces_to_dotresi` and the CLI
  but to `4.8.0` in `to_dotresi` and `change_instrument_id`, undocumented.
- The module docstring lists `regVar` among the elements the app writes;
  neither real sample has it.
- The `trace.py` todo list still says "move to using pyproject.toml";
  `get_comment` and `get_remark` duplicate each other.
- `pytest addopts` ignores `test_all_dotresi.py`, which doesn't exist.

## 5. Tests

- Some tests assert the bugs: `test_dotresi.py:473` (`"DOB" not in
  df.columns`), `test_trace.py:281` (bark thickness), and the 39-vs-43 column
  comment has the counts the wrong way round.
- No round-trip test compares against the source file's raw columns.
- DuckDB and some `.Resi` loading tests use files under `/home/jh/`, so they
  skip anywhere else.
- The Delta parity tests only compare the Python engine with Spark, import
  `deltalake` at module top, need `PYSPARK_PYTHON` set, and aren't installed
  by tox.
- Missing: SQL identifiers, date/time parsing, `pd.NA` values, copy/pickle,
  merging into a `DeltaTable` or remote table, and reading pre-0.0.46 files
  that store FeedSpeed as 200 (cm/min).
